# V2: Ask-graph tracing

Batch 4. Contract: `docs/capstone/batch4.md` sections 34–35. V1 built `governor.core.runtrace`; reuse it.

Rules for the whole batch (contract §33): no behaviour change when the console is unused, no data values in anything new (counts, names, codes, statuses, durations, tokens, cost only), build and ask never import each other or integrations, code owns every edge, `evaluation/` and `knowledge/` untouched, existing tests unchanged, tests offline.

Build:
1. `runtrace.registry`: the ask graph's node specs (groups `understand`, `sql`, `answer`), edge labels for every conditional edge, and `topology("ask")`.
2. `src/governor/ask/graph.py`: wrap each node where the builder adds it (one loop today) with `traced("ask", ...)` and a summariser per node (§35 ask table). Never the question, SQL, answer or a row value; `execute` may report the row count only.
3. `src/governor/ask/checkpoints.py` (`invoke` is the one funnel for ask calls): emit `run_started` (new thread) or `run_resumed` (a `Command(resume=...)`), and `run_finished` with the final status when the thread ends. A clarify interrupt is `run_paused` with `awaiting_clarification`. Status names: map the graph's end state to `answered`, `refused`, `blocked` or `error`; keep the mapping in one function.
4. Nothing in the ask API responses, `traces.duckdb` or the certified path changes.

Tests (`tests/ask/`):
- `test_ask_registry_matches_graph`, `test_ask_conditional_edges_labelled`
- `test_ask_run_log_answered_after_repair` (scripted LLM: a first SQL refused by the validator, a repair, then answered; validate has attempt 2)
- `test_ask_run_log_guard_blocked` (ends `run_finished` status `blocked`/`refused`; most nodes skipped in `fold`)
- `test_ask_clarify_is_pause`
- `test_ask_run_log_has_no_text_or_values` (marker strings in the question, the SQL and a result cell never appear in the log)
