# F6: One Slack bot for several tenants

Batch 3. Contract: `docs/capstone/batch3.md` section 32. Decision: `docs/adr/0004-maintain-mode-and-tenancy.md`.

Rules for the whole batch (contract, top): no behaviour change when the feature is unused, no data values in anything new, code owns every edge, `evaluation/` untouched, existing tests unchanged unless the contract names them.

Build:
1. Slack config: targets from the registry when `GOVERNOR_TENANTS` is set, with the start-up warning about `GOVERNOR_SLACK_TARGETS` (32.1).
2. Route run, approve, reject, publish and the buttons to one tenant; resolve the tenant of a thread from each tenant's checkpoints; an ambiguous short id is a usage error naming both tenants (32.2).
3. Name the tenant in progress messages, design cards and replies; list tenants in the start-up line and the usage footer (32.3).
4. `/governor ask` in multi-tenant mode: the ephemeral refusal of 32.4, nothing run.
5. `docs/tenants.md` (32.5) and a short section in `docs/slack.md`.

Tests (`tests/integrations/`):
- `test_targets_come_from_tenant_registry`
- `test_run_routes_to_its_tenant`
- `test_approve_resolves_tenant_from_thread`
- `test_thread_in_two_tenants_is_a_usage_error`
- `test_ask_refused_in_multi_tenant_mode`
- `test_messages_name_the_tenant`

Use the fake Slack client and inline runner of `tests/integrations/`; a fake build object records which tenant each call received. Existing Slack tests stay unchanged and green.

Read: `docs/capstone/batch3.md` section 32, `src/governor/core/tenancy.py`, `src/governor/integrations/slack/*.py`, `tests/integrations/`.
